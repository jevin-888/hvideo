# 多设备同步播放方案建议

> 状态：UDP 4322 组播、跨设备时钟校准、定时首帧启动和运行中漂移纠偏已落地；真机精度验收仍需按第 13 节执行。
>
> 适用范围：多台运行 HSVJEngine 的 Android/嵌入式播放设备，在同一个局域网内同时播放同一份视频或音频素材。

## 1. 结论先行

建议采用 **Leader/Follower（主设备/从设备）+ 本地素材 + 统一逻辑时钟 + 定时启动 + 持续纠偏** 的方案：

1. 由一台设备担任 Leader，负责接收外部控制、执行一次命令并下发控制决策。
2. 每台设备先准备自己的本地素材，不在播放过程中把 Leader 的视频帧实时转发给其他设备。
3. 主设备把已经通过 `CommandRouter` 校验的规范化命令，通过独立 UDP `4322` 组播分发给组内机器；Follower 通过同端口单播 UDP 回 ACK；继续使用现有 UDP `18080` 做设备发现。
4. 通过四时间戳测量把各设备的 `steady_clock` 映射到 Leader 时钟，所有动作使用单调时钟，不使用墙上时间（Unix 时间）。
5. 启动时间预留约 350 ms 的短准备窗口，所有设备在同一个 `startAtLeaderMonoNs` 到达时开始播放，避免本地切换出现明显等待。
6. 播放中按 2 Hz 上报状态，Leader 根据位置误差选择“忽略、微调速率、纠偏 seek、重新缓冲”四级策略。
7. 同步会话只负责编排，不复制播放状态；真正的播放仍必须经过 `PlaybackCoordinator`/`PlaybackRequestDispatcher`。

在常见的千兆以太网或稳定的 5 GHz Wi-Fi 环境下，首版目标应设为：视频 P95 误差不超过 40 ms、P99 不超过 80 ms；音频 P95 不超过 20 ms。若业务要求长期稳定在 10 ms 以内，再评估 PTP/gPTP 和硬件时间戳。

### 1.1 对“UDP 分组 + 主设备转发”的评价

这个思路可以作为主方案，但要把“UDP 分组”定义为 **组播命令分发通道**，不能理解成“收到什么原始字符串就原样转发什么”。推荐的原则是：

- 主设备（Leader）是组内唯一的外部控制入口，接收 RS232、RS485、TCP、普通 UDP、HTTP 和控制端命令。
- 主设备先把不同来源的输入转换成统一的领域命令，再在本机执行一次，同时向组播地址发布同一个 `commandId/epoch/seq`。
- 从设备（Follower）只接受已认证的 Leader 组播命令；收到后去重、校验、受控执行，并单播回复 `received/applied/not_ready`。
- 组播只负责“一次发给所有机器”，不保证到达。关键动作必须配合 ACK、超时、重发和状态快照，否则一台丢包的机器会悄悄偏离。
- 现有 UDP `8000` 是外部命令入口，不建议直接与同步组播混用。同步端口固定为 UDP `4322`，并在设备发现结果中发布 `ports.sync`（未启用时为 `0`）。

因此，当前实现已经覆盖可追踪组命令、跨设备时钟、未来时刻启动和运行中纠偏；关键 UDP 信封会做有限同序号重发，接收端用滑动窗口去重，播放接收在独立工作队列执行，并在状态偏离时自动恢复。

### 1.2 当前代码范围

- 已实现：Leader/Follower 配置、固定 UDP `4322`、`hsvj.sync.v1` JSON 信封、组播命令、Follower 去重、单播 ACK、回环抑制、同步端口发现和生命周期管理。
- 已接入：所有成功的设备执行类命令都通过 `CommandRouter` 复制到组内，包括播放、场景、图层、外设、舞台协议、实时 DMX `0x51` 和系统控制 `0x10`；查询类动作以及文件编排 `sync_device` 保持本地/专用事务。
- 已实现：四时间戳时钟探测（`clock_probe/reply/sync`）、`sync_prepare/sync_start` 未来时刻调度、2 Hz 状态上报和按误差分级的速率/seek 纠偏。
- 当前边界：ACK 用于结果观测和重复包确认，尚未实现“等待全部节点 ACK 后才提交”的强一致屏障；素材 manifest 自动校验仍需部署前完成，组播不可用时依赖已注册节点的同步单播。

## 2. 现有项目如何承接

| 现有能力 | 在同步播放中的职责 | 约束 |
|---|---|---|
| `DeviceDiscoveryService`，UDP `18080` | 发现设备、读取 `ip`、设备身份、`ports.ws` 和 `ports.sync` | 不新增第二套发现协议；连接端口以发现结果为准，不硬编码 `8090`/`9898`/`4322` |
| `UdpServer`（现有 `8000`） | 接收外部 UDP 命令，不直接承担组播同步 | 不把组播报文重新交给普通外部命令入口 |
| `SyncUdpGroup`（独立传输） | 加入组播、发布 Leader 命令、接收 Follower 命令 | 使用固定 UDP `4322` 和 `hsvj.sync.v1` 信封；TTL/网卡可配置 |
| `WebSocketServer` | 现有状态广播；同步状态继续走 UDP `4322` | 不改变既有状态广播格式 |
| `NetworkManager` | 管理 UDP 组播、WebSocket 生命周期和消息转发 | 同步服务随 Engine 启停，不能自行创建重复网络服务 |
| `PlaybackCoordinator` | 所有 prepare/start/pause/seek/stop 最终执行点 | 同步调度通过 `PlaybackRequestDispatcher`，不绕过播放架构 |
| `PlaybackRequestDispatcher` | 将会话中的播放请求转换为统一播放请求 | 保留已有资源门、镜像限制、蓝牙音频限制和诊断链路 |
| `LayerVideo`/Decoder | 接收未来 `syncStartTime`、提供当前状态和媒体位置 | 位置来自解码时钟；播放速率修改使用原子值避免纠偏线程竞态 |
| `Engine` | 组合根、生命周期、状态广播和退出清理 | 会话退出时先停止同步任务，再停止网络和播放资源 |

仓库当前 HTTP 公开协议只使用 `/api/v1`，动作统一使用 `/api/v1/{module}/actions/{action}`。同步控制若需要 HTTP 入口，建议只增加一组：

```text
POST /api/v1/sync/actions/{action}
GET  /api/v1/sync/session
GET  /api/v1/sync/status
```

`{action}` 只允许 `create`、`join`、`leave`、`prepare`、`start`、`pause`、`seek`、`stop`。不要再增加 `/sync/start`、`/sync/pause` 等平铺别名；实现路由时必须同步 `HttpServer_Sync.cpp`、Web/Flutter 调用点和自动生成的 API 文档。

## 3. UDP 分组和主设备职责

### 3.1 分组配置

每台机器保存同一个 `groupId`，从设备配置主设备的 `leaderIp`。组播地址和网卡 IP 可配置；同步端口固定为 UDP `4322`，建议使用管理范围组播地址，不使用保留给本地链路协议的 `224.0.0.x`：

```json
{
  "syncGroup": {
    "enabled": true,
    "groupId": "stage-a",
    "role": "leader",
    "leaderIp": "192.168.2.103",
    "multicastAddr": "239.255.42.10",
    "port": 4322,
    "interface": "",
    "ttl": 1
  }
}
```

主设备和每台从设备只需要保持 `groupId`、`multicastAddr`、`port`、`ttl` 一致；从设备把 `role` 设为 `follower`，并把 `leaderIp` 填成主设备在同步网卡上的 IPv4 地址。例如：

```json
{
  "syncGroup": {
    "enabled": true,
    "groupId": "stage-a",
    "role": "follower",
    "leaderIp": "192.168.2.103",
    "multicastAddr": "239.255.42.10",
    "interface": "",
    "port": 4322,
    "ttl": 1
  }
}
```

保存配置后重启 Engine；默认 `enabled=false`，不会改变既有单机部署。

`interface` 留空表示自动选择；多网卡设备应保存实际网卡 IP，而不是网段地址。生产部署应把 TTL 设为 1，避免控制命令跨越路由器。

不要把同步组播绑定到现有设备发现端口 `18080`，也不要直接复用外部 UDP 命令端口 `8000`。后者当前会把收到的报文记录客户端、调用外设触发匹配并交给 `CommandRouter`，混用会产生重复执行和回环风险。当前使用只处理 `hsvj.sync.v1` 的 `SyncUdpGroup`，由 `NetworkManager` 统一管理。

### 3.2 命令流

```text
RS232 / RS485 / TCP / 外部 UDP / HTTP / 控制端
                         |
                         v
Leader 的现有入口 -> CommandRouter 规范化与权限校验
                         |
              +----------+----------+
              |                     |
              v                     v
       Leader 本机执行一次       UDP 组播 `command`
                                      |
                           +----------+----------+
                           v                     v
                    Follower 去重/校验       Follower ACK
                           |                     |
                           v                     v
                   PlaybackCoordinator     Leader 记录 ACK
```

主设备不能把 RS232 字符串、TCP 原始帧或 UDP 原文直接广播。不同入口的编码、参数和权限不一致，原样转发会让从设备各自解释出不同结果。应在 Leader 中先得到统一的领域命令，例如：

```json
{
  "action": "playlist.play",
  "playlistId": "night-show",
  "itemIndex": 4,
  "layerId": 1,
  "applyAtLeaderMonoNs": 987655821000
}
```

`playlistId`、`sceneId`、`mediaId` 等资源标识优先于本地路径；路径只在每台机器的本地资源索引中解析。

### 3.3 哪些命令可以同步

| 命令类别 | 默认策略 | 说明 |
|---|---|---|
| 场景切换、播放列表播放、播放/暂停/继续/跳转/停止 | 组内同步 | 带 `epoch`、`seq` 和统一执行时间 |
| 画面效果、图层显隐、亮度等运行态设置 | 组内同步 | 必须声明是否需要屏障确认 |
| 网络配置、端口、授权、固件升级、重启 | 组内同步（高风险动作仍需权限） | 主设备收到并成功执行后复制到从设备；执行前应确认会导致网络/进程中断 |
| 串口/UDP/TCP/WebSocket 数据转发、舞台协议、实时 DMX | 组内同步 | 统一成 `0x50`/`0x51` 命令；二进制 payload 以 hex 传输，避免 JSON/UTF-8 损坏 |
| 调试日志、设备诊断和查询 | Leader-only 或本地 | 无设备副作用，不复制查询结果和诊断输出 |
| 急停/安全停机 | 组内高优先级 | 允许立即执行，仍带 `commandId` 并回执 |

Follower 默认关闭外部控制入口，或者只接受本地急停；如果 Follower 也能接收普通 RS232/RS485/TCP 命令，就会破坏“单一主设备事实源”。

### 3.4 可靠性和回执

UDP 组播没有顺序、到达和重传保证，建议每条组命令包含：

```text
groupId + sessionId + epoch + seq + commandId + commandType + payload
```

当前实现的 Follower 按 `(groupId, sessionId, epoch, seq)` 去重；处理结果通过 UDP `4322` 单播 ACK 回 Leader。Leader 记录 `received/applied/not_ready/duplicate/error` ACK 日志，便于部署验收。

当需要“所有节点确认后才切换”的强一致场景，仍应在下一阶段增加节点清单和提交屏障。当前版本已经提供有限重发和结果 ACK：

- 普通状态命令：状态快照每 500 ms 发送一次，短暂丢包由下一次快照覆盖。
- 播放、场景、跳转等关键命令：同一信封最多重发 2 次；Follower 只执行一次并对重复包回 ACK。
- 仍未确认：由 Follower 的状态自愈路径按 Leader 快照重新播放、暂停或停止；控制端仍应观察 ACK 日志判断是否需要人工介入。
- Follower 重连：不补发历史 UDP 包，只请求 Leader 的当前会话快照和当前播放位置。

若交换机或 Wi-Fi AP 不支持/不转发组播，`SyncUdpGroup` 应回退到已发现节点的单播 UDP；消息格式和序列规则保持不变，不增加第二套命令协议。

### 3.5 每日配置和素材一致性

“每天机器配置一样”应落成可校验的 `manifest`，而不是依赖人工保证：

```json
{
  "manifestId": "2026-08-30-stage-a",
  "configHash": "sha256:...",
  "sceneCatalogHash": "sha256:...",
  "playlistHash": "sha256:...",
  "assetManifestHash": "sha256:..."
}
```

Leader 创建或启动会话前广播 manifest；Follower 启动时上报本地 hash。任一必需 hash 不一致，Follower 回复 `MANIFEST_MISMATCH` 并保持 `NOT_READY`，不能用“看起来相同”的名称继续播放。配置和素材更新应先生成新 manifest，再切换到新的 `epoch`。

发生不一致时，使用现有素材下载/维护链路（例如 `/api/v1/materials/download`）或离线介质修复；UDP 组播只传 manifest 和控制命令，不承担大文件分发。

## 4. 目标和非目标

### 4.1 首版目标

- 2 至 8 台设备在同一局域网内同步播放同一素材。
- 支持统一开始、暂停、继续、跳转、停止。
- 支持设备加入、离开、断线重连和 Leader 主动结束会话。
- 播放期间可观测每台设备的时钟偏移、RTT、缓冲量、位置误差和纠偏次数。
- 设备素材可以预先通过 U 盘、下载、共享目录或现有素材管理能力分发。

### 4.2 首版不做

- 不把 Leader 解码后的每一帧实时推送到所有设备。
- 不把同步状态写入现有播放列表数据库；会话是运行时状态。
- 不允许多个 Leader 同时写同一个会话。
- 不把 Android `System.currentTimeMillis()` 当作跨设备时钟。
- 不在同步模块旁路 `PlaybackCoordinator` 建立另一套解码/播放状态。

## 5. 推荐架构

```text
控制端/平板
      |
      | HTTP /api/v1/sync/actions/{action}
      v
Leader Engine
  |  SyncSessionManager（会话、选主、时钟、编排）
  |        |
  |        +-- SyncUdpGroup：组播 `command`
  |        +-- WebSocket/单播：ACK、状态、时钟探测
  |        +-- steady_clock 映射与漂移计算
  |
  +-- PlaybackCoordinator -> LayerPlaybackController -> LayerVideo/Decoder
                                   |
                                   +-- VulkanRenderer -> 当前输出后端

Follower Engine（每台结构相同）
  SyncUdpGroup/WebSocket -> SyncSessionManager -> PlaybackCoordinator -> LayerVideo/Decoder
```

### 5.1 媒体平面和控制平面分离

控制平面只发送小型 JSON 控制消息和状态；媒体平面由每台设备从本地文件读取。素材身份不能只使用路径，应使用：

```json
{
  "mediaId": "sha256:...",
  "sizeBytes": 123456789,
  "durationMs": 180000,
  "container": "mp4",
  "video": {"codec": "h264", "width": 1920, "height": 1080, "fps": 30.0},
  "audio": {"codec": "aac", "sampleRate": 48000, "channels": 2}
}
```

Follower 以 `mediaId` 查本地索引，路径仅作为当前设备的内部映射。这样可以避免不同设备目录不同、文件被替换或路径包含特殊字符导致误播。

### 5.2 会话状态机

```text
IDLE
  -> CREATING -> PREPARING -> ARMED -> PLAYING
                                  |         |
                                  |         +-> PAUSED
                                  |                 |
                                  +<----------------+
  任意状态 -> SEEKING -> ARMED/PLAYING
  任意状态 -> STOPPING -> IDLE
  任意状态 -> DEGRADED/ERROR
```

每个发送会话带基于墙钟启动纪元的 `epoch` 和唯一 `sessionId`；消息同时带单调递增 `seq`。Follower 按“发送方/会话/消息类型”使用 64 位滑动窗口去重，允许 UDP 乱序但拒绝重复和旧会话；主设备进程重启或本机 IP 变化后会生成新会话并重新校时。

## 6. 时钟同步设计

### 6.1 时钟原则

- 使用 C++ `std::chrono::steady_clock` 或 Android `elapsedRealtimeNanos()`；两者只能在本机使用。
- 播放调度只维护“Follower 本地单调时钟相对 Leader 的偏移”。系统日期时间独立按第 6.5 节对时，系统时间跳变不改变播放单调时钟。
- 所有时间字段使用整数纳秒（`int64`），展示和 HTTP 参数可使用毫秒。
- 保存偏移估计的不确定度；不确定度过大时不能宣称已同步。

### 6.2 四时间戳探测

Leader 发出探测时记录 `t0`，Follower 收到和发出响应时记录 `t1`、`t2`，Leader 收到响应时记录 `t3`：

```text
offset(Follower - Leader) = ((t1 - t0) + (t2 - t3)) / 2
rtt                       = (t3 - t0) - (t2 - t1)
```

实现建议：每轮发送 8 个样本，丢弃 RTT 高于本轮中位数 2 倍或高于 100 ms 的样本，使用剩余样本的中位数作为偏移；启动前至少完成 3 轮，播放中每 2 秒更新一次。把 `offsetMs`、`rttMs`、`jitterMs` 和 `uncertaintyMs` 放入诊断状态。

### 6.3 定时启动流程

1. Leader 创建会话并锁定 `sessionId`、`epoch`、媒体指纹、目标图层和播放模式。
2. Leader 广播 `prepare`，`startAtLeaderMonoNs` 默认设为当前 Leader 单调时间加 350 ms。
3. Follower 先做素材可用性/媒体探测并回复 `ready` 或带原因的 `not_ready`；真正解码器启动留到统一的本地目标时刻。
4. Leader 发送 `sync_start`（当前版本预留 350 ms 准备窗口）；Follower 按 ready 结果排队，未就绪节点明确记录而不会静默伪装成功。
5. 每台设备将目标时间转换为自己的本地单调时间：

```text
startAtFollowerMonoNs = startAtLeaderMonoNs + offset(Follower - Leader)
```

6. 到达本地目标时间后调用统一播放协调器开始播放，首帧实际呈现时间记入诊断。

### 6.4 位置估算

每台设备保存播放锚点：`anchorLocalMonoNs`、`anchorMediaPtsMs`、`rate`。在播放状态下：

```text
localPositionMs = anchorMediaPtsMs
                  + (localNowMonoNs - anchorLocalMonoNs) / 1e6 * rate
```

Follower 把自己的位置和时钟偏移上报给 Leader。Leader 先把当前 Leader 时间映射到 Follower，再计算目标位置：

```text
targetPositionMs = startPtsMs
                 + (leaderNowMonoNs - startAtLeaderMonoNs) / 1e6 * rate
driftMs          = localPositionMs - targetPositionMs
```

`driftMs > 0` 表示 Follower 超前，`driftMs < 0` 表示落后。

### 6.5 云端 NTP 与组主机系统时间回退

- 仅启用同步组的 Follower 接收已配置 `leaderIp`（或原有 `leaderDeviceId`）对应主机的授时；Leader 继续使用自己的 Android NTP/本地时钟，不向从机取时。
- `clock_sync.payload` 增加两个可选整数：`leaderUtcMs` 是 UTC Unix 毫秒，`leaderMonoNs` 是取该 UTC 样本时的 Leader 单调纳秒。接收端用 `localMonoNs = leaderMonoNs + offsetNs` 映射样本，再用本地单调时间补偿传输和排队延迟。原 `offsetNs`、`rttNs` 单位和播放语义保持不变。
- 只接受当前组、指定主机、当前会话、已回复探测的 `probeId`。探测超过 5 秒或 RTT 超过 250 毫秒则丢弃；UTC 必须在 2020 至 2100 年之间。旧版主机缺少 UTC 字段时仍可同步播放，但不能提供系统时间回退。
- Android `AUTO_TIME=1` 时，收到新鲜主机样本后最多每 60 秒查询一次系统 `ntp_server`，空值沿用 H6 ROM 默认 `ntp.aliyun.com`。后台线程复用 Android `SntpClient`，UDP 响应超时 3 秒；DNS 由 Android Network 解析。
- 云端查询成功优先使用 NTP；失败或无有效云端样本时，使用最近 5 秒内的组主机 UTC。主机样本也过期则保持本地时钟。组停用、身份/主机会话变化会立即撤销旧样本；查询返回后重新检查会话和自动时间开关，避免迟到结果改时。
- 使用已有 `SET_TIME` 权限调用 `AlarmManager.setTime`，偏差达到 2 秒才写入；不修改 `AUTO_TIME`、时区或 NTP 服务器配置。来源日志为 `[GroupTimeSync] source=cloud_ntp/udp4322_leader/local_holdover`。
- 该路径更新系统时钟，不伪造 Android NTP 缓存。因此离线时系统仍可能输出 `BestClock: Missing NTP fix`，应结合 `GroupTimeSync` 来源和实际系统时间判定对时是否成功。

## 7. 消息协议建议

所有同步消息（无论通过 UDP 组播、单播 UDP 还是 WebSocket）使用同一 JSON 信封，不复用旧的 `type/code/param` 数字命令字段。`transport` 只用于诊断和路由，不改变业务字段：

```json
{
  "protocol": "hsvj.sync.v1",
  "transport": "multicast",
  "type": "prepare",
  "sessionId": "01J...",
  "epoch": 3,
  "seq": 17,
  "senderId": "device-serial-or-mac",
  "sentAtMonoNs": 123456789000,
  "payload": {}
}
```

推荐的消息类型和用途：

| 类型 | 方向 | 关键字段 | 幂等规则 |
|---|---|---|---|
| `hello` | 双向，单播/WebSocket | `deviceId`、能力、协议版本 | 连接建立后发送一次 |
| `clock_probe` | Leader -> Follower，UDP `4322` 组播 | `probeId`、`t1` | 同一 `probeId` 只响应一次 |
| `clock_reply`/`clock_sync` | Follower <-> Leader，UDP `4322` 单播 | `probeId`；reply: `t1/t2/t3`；sync: `offsetNs/rttNs`、可选 `leaderUtcMs/leaderMonoNs` | 同会话未过期探测匹配；缺少 UTC 扩展只影响系统对时 |
| `command` | Leader -> 组内，UDP 组播 | `commandId`、`commandType`、`applyAtLeaderMonoNs`、业务参数 | `(epoch, seq, commandId)` 去重 |
| `sync_prepare` | Leader -> 组内，UDP 组播 | 规范化命令、`scheduleId`、`startAtLeaderMonoNs` | 同 `epoch` 重复 prepare 返回同一结果 |
| `ready`/`not_ready` | Follower -> Leader | `mediaId`、`decoderReady`、`bufferMs`、`reason` | 以 `epoch` 和节点 ID 去重 |
| `sync_start` | Leader -> 组内，UDP 组播 | `scheduleId`、`startAtLeaderMonoNs`、规范化命令 | 已执行的 `seq` 不重复执行 |
| `pause`/`seek`/`stop` | Leader -> 组内，UDP 组播 | 新 `epoch`、目标位置或时间 | 只接受最新 `epoch` |
| `state` | Follower -> Leader | 状态、位置、缓冲、偏移、RTT | 只保留每节点最新状态 |
| `adjust` | Leader -> Follower，单播/WebSocket | `targetPositionMs`、`mode`、`durationMs` | 过期目标不执行 |
| `error` | 双向 | 错误码、可重试标记 | 错误码必须可统计 |

示例 `prepare`：

```json
{
  "protocol": "hsvj.sync.v1",
  "transport": "multicast",
  "type": "prepare",
  "sessionId": "sync-20260829-0001",
  "epoch": 1,
  "seq": 4,
  "senderId": "leader-001",
  "sentAtMonoNs": 987654321000,
  "payload": {
    "media": {"mediaId": "sha256:abc...", "durationMs": 180000},
    "layerId": 1,
    "startPtsMs": 0,
    "startAtLeaderMonoNs": 987655821000,
    "rate": 1.0,
    "required": true
  }
}
```

## 8. 漂移纠正策略

不要每次检测到误差就 seek。频繁 seek 会触发解码器释放/重建，反而造成更大抖动；应按误差分级：

| 绝对误差 | 动作 | 建议参数 |
|---:|---|---|
| `< 15 ms` | 忽略 | 保持 `rate=1.0` |
| `15-60 ms` | 微调播放速率 | `0.995-1.005`，在 1-2 秒内平滑回正 |
| `60-250 ms` | 计划内 seek | 选择最近可用关键帧，完成后恢复 `1.0` |
| `> 250 ms` 或缓冲不足 | 暂停/重新缓冲/硬纠偏 | 重新计算本地目标时间，记录一次 hard resync |

微调速率必须有上下限、持续时间和取消条件，不能由多个线程同时改写 `LayerVideo::setPlaybackRate`。建议由每个同步会话单线程调度，其他线程只投递事件。

`pause`、`seek`、`stop` 属于全局屏障操作：Leader 先广播新 `epoch`，Follower 回复 `applied` 后再进入下一阶段。超时节点进入 `DEGRADED`，不能继续以旧 epoch 播放。

## 9. 断线、加入和 Leader 故障

### 9.1 Follower 断线

- 连续 3 个状态周期（约 1.5 秒）未收到 Leader 消息，进入 `DEGRADED`，保持当前画面或按策略暂停。
- 断线重连后先发送 `hello` 和本地 `lastSessionId/epoch/seq`，等待 Leader 下发完整快照，不直接补发旧控制消息。
- 若已超过可接受误差，执行一次硬纠偏；若素材不存在，回复明确的 `MEDIA_NOT_FOUND`。

### 9.2 Leader 故障

首版建议 **不自动选主**，由控制端重新创建会话，避免双 Leader 分裂。若后续确实需要无人值守，再引入租约：Leader 每 1 秒续租，Follower 观察到连续 3 秒无租约后，按设备 ID 排序选主并递增 `term`。`term` 必须高于 `epoch`，用于防止旧 Leader 恢复后继续发指令。

### 9.3 中途加入

只允许加入 `PREPARING` 或 `PLAYING` 会话。新 Follower 完成素材和解码器准备后，Leader 发送一个未来至少 1 秒的 `startAt`，从当前目标位置开始；不要让它从文件头播放再追赶。

## 10. API 与权限建议

### 10.1 HTTP 控制入口

HTTP 仅用于控制端发起会话和查询，不用于高频时钟校正。建议请求体示例：

```json
POST /api/v1/sync/actions/create
{
  "mediaId": "sha256:abc...",
  "layerId": 1,
  "deviceIds": ["board-001", "board-002"],
  "startMode": "barrier",
  "requiredReady": true
}
```

成功响应继续使用仓库统一格式 `{"ok":true,"data":...,"error":null}`；失败响应继续使用 `{"ok":false,"data":null,"error":{...}}`。WebSocket 的 `error` 也应沿用稳定的错误码，避免 HTTP 和 WS 各自定义一套含义。

建议错误码：`SYNC_SESSION_NOT_FOUND`、`SYNC_NOT_LEADER`、`SYNC_EPOCH_STALE`、`SYNC_MEDIA_NOT_READY`、`SYNC_CLOCK_UNCERTAIN`、`SYNC_NODE_TIMEOUT`、`SYNC_UNSUPPORTED_CAPABILITY`。

### 10.2 身份和授权

- 同步节点标识优先使用本机 IPv4 地址，与从设备配置的 `leaderIp` 保持一致；仅在网络尚未就绪时回退到 MAC/序列号。
- 组播被交换机或 AP 隔离时，从设备会通过 `leaderIp:4322` 注册，Leader 将同步信封同时单播给已注册节点；因此同一局域网只要设备间 UDP 单播可达即可工作。
- 使用现有登录/授权机制取得控制权限；会话创建时生成随机 `sessionId`。
- 局域网仍需校验 Leader allowlist，至少拒绝未知设备加入。
- 生产环境可在 WebSocket 信封外增加 HMAC；签名覆盖 `protocol/type/sessionId/epoch/seq/payload`，防止局域网重放和篡改。

## 11. 代码落地建议

按现有模块边界分阶段增加，避免把网络协议、时钟算法和解码器控制揉成一个大类：

| 阶段 | 建议文件/模块 | 主要内容 |
|---|---|---|
| 协议 | `include/network/SyncProtocol.h`、`src/network/SyncProtocol.cpp` | JSON 信封、版本、字段校验、错误码、序列化 |
| 会话 | `include/network/SyncSessionManager.h`、`src/network/SyncSessionManager.cpp` | Leader/Follower 状态机、节点表、租约（首版可关闭） |
| 时钟 | `include/network/SyncClock.h`、`src/network/SyncClock.cpp` | 四时间戳、样本过滤、偏移/不确定度 |
| 播放编排 | `include/playcontrol/SyncPlaybackScheduler.h`、`src/playcontrol/SyncPlaybackScheduler.cpp` | prepare/arm/start、屏障、漂移纠正；内部调用 `PlaybackCoordinator` |
| 组播传输 | `include/network/SyncUdpGroup.h`、`src/network/SyncUdpGroup.cpp` | 已实现：独立端口、加入/离开组播、TTL/网卡、收发 `hsvj.sync.v1` 的 `command`/`ack` |
| 网络接入 | `src/network/NetworkManager.cpp` | 已实现：组播生命周期、ACK 日志、广播隔离；不把同步包送回普通 `CommandRouter` |
| HTTP | `src/network/HttpServer_Sync.cpp` | 只注册 `/api/v1/sync/actions/{action}`、`/session`、`/status` |
| 组合根 | `src/core/Engine.cpp`、`src/core/Engine_Init.cpp`、`src/core/Engine_Update.cpp` | 初始化、周期 tick、退出顺序、状态广播 |
| 控制端 | `src/network/web/`、`Fultter_pad/` | 设备选择、会话状态、误差诊断；不在客户端自行计算播放真相 |

`PlaybackRequest` 现有字段（图层、路径、循环、来源、优先级、请求 ID）应继续作为统一入口。若 prepare 需要预加载能力，优先在 `LayerPlaybackController` 增加内部 `arm/commit` 语义或新增 `SyncPlaybackPlan`，不要把 `sessionId/epoch` 直接散落到各个解码器。当前组播报文由 Leader 侧的规范化命令观察器发布，并由 Follower 侧的受控分发器调用 `CommandRouter`/`PlaybackCoordinator`，不得通过普通外部 UDP 分支再次触发转发。

## 12. 分阶段实施

### Phase 0：测量基线（1-2 天）

- 在现有播放状态中记录单调时钟、首帧呈现时间、`getPlaybackPositionMs()`、缓冲和解码器状态。
- 先测同一设备重复 start 的抖动，再测两台设备同时收到普通 HTTP 命令的抖动。
- 建立日志字段：`sessionId`、`epoch`、`seq`、`deviceId`、`event`、`localMonoNs`、`positionMs`、`driftMs`。

### Phase 1：会话和素材预检（2-4 天）

- 复用 `DeviceDiscoveryService` 找到设备并读取 `ports.ws`/`ports.sync`，让 Follower 加入指定组播地址。
- 实现 `hello`、`create/join/leave`、manifest 校验、素材指纹校验和 `prepare/ready`。
- 验证组播不可用时的单播回退，不把失败伪装成全组成功。
- 暂不做漂移校正，只验证设备能否在 `ARMED` 屏障后稳定等待。

### Phase 2：统一时钟和定时启动（已实现）

- 加入四时间戳探测和偏移过滤。
- 通过 UDP 组播发送带 `applyAtLeaderMonoNs` 的规范化 `command` 和未来时间点的 `start`，记录计划启动与实际首帧差值。
- 支持统一 `pause/seek/stop` 和 epoch fencing。

### Phase 3：持续纠偏和故障恢复（纠偏已实现，故障恢复待补）

- 2 Hz 状态上报和四级纠偏已实现；ACK/重发/快照、缓冲不足处理待补。
- 实现 Follower 重连快照和一次 hard resync。
- 增加 Web/Flutter 诊断视图，但不增加第二套控制状态。

### Phase 4：真机验收和性能优化（持续）

- 先覆盖 2 台，再覆盖 4 台、8 台；分别测试有线、5 GHz Wi-Fi、2.4 GHz Wi-Fi，并验证交换机/AP 的 IGMP 组播行为。
- 只有在测量证明应用层同步无法满足指标时，才评估 PTP/gPTP 或硬件时间戳；独立 UDP 同步端口已经是本方案的默认隔离方式。

## 13. 测试和验收标准

### 13.1 自动化测试

- `SyncClock`：无延迟、对称延迟、非对称延迟、时钟漂移、异常 RTT 样本。
- 状态机：重复消息、乱序消息、旧 epoch、重连快照、节点超时。
- 漂移控制：四个误差区间分别触发正确动作，速率始终在上下限内。
- 协议：缺字段、未知版本、超长 `sessionId`、非法图层、重复 `seq`、错误 `groupId`、伪造 Leader。

### 13.2 真机测试

- 使用同一视频中固定亮度闪光帧或音频点击作为测量标记；用高速摄像机/光电传感器测设备间差值，不只看肉眼。
- 每个网络条件至少采集 100 次 start、20 次 seek、20 次 pause/resume。
- 注入 1%、5% 丢包、重复包、乱序包和短时组播不可达，确认关键命令能重发或明确失败。
- 验收指标：

| 指标 | 目标 |
|---|---:|
| 设备发现成功率 | 100%（同网段、5 秒内） |
| `prepare` 就绪结果可解释率 | 100%（成功或明确错误码） |
| 启动首帧 P95 差值 | 视频 <= 40 ms；音频 <= 20 ms |
| 启动首帧 P99 差值 | <= 80 ms |
| 播放 10 分钟后的 P95 漂移 | 视频 <= 40 ms |
| 单次普通纠偏造成的可见中断 | <= 1 次/10 分钟 |
| 断线重连后的恢复 | 5 秒内完成快照或明确失败 |

## 14. 方案取舍

| 方案 | 优点 | 主要问题 | 建议 |
|---|---|---|---|
| 本地素材 + Leader/Follower + UDP 组播（本文） | 带宽低、一次发给全组、可复用现有解码链路 | UDP 需自行做 ACK/重发，依赖网络组播配置 | **首选** |
| Leader 实时推流（RTSP/WebRTC） | 素材只维护一份 | 网络抖动直接变成播放抖动；多路解码/转发成本高 | 不作为首版 |
| 只同时发送 play 命令 | 实现最简单 | 各设备启动延迟和时钟漂移无法控制 | 仅可做临时演示 |
| PTP/gPTP 硬件同步 | 理论精度最高 | Android、网卡和交换机支持不一致，部署复杂 | 达标压力明确后再做 |

## 15. 需要产品在实施前确认的选项

1. 同步对象是“同一内容多屏”，还是“多设备协同播放不同内容”；本文按前者设计。
2. 设备规模上限是 8 台还是更大；超过 8 台应考虑分层 Leader 或组播。
3. 音频是否由多台设备同时外放；若是，验收阈值应按音频而不是视频标准执行。
4. 素材分发是 U 盘/人工拷贝、现有下载接口，还是统一 NAS；这决定 `mediaId` 到本地路径的实现。
5. Leader 故障时是否允许自动选主；首版默认人工重建会话，优先保证一致性。
